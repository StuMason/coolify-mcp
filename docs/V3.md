# V3 (#259): SDK v2 + dual transport

Working notes for the v3 branch. **Nothing on this branch releases until it has
been tested hard on a real estate** — that is a standing instruction, not a
preference.

## Verified facts (scripts/v3-spike.mjs — run it, don't trust this file)

SDK v2 shipped 2026-07-28 as split packages, not a major bump of the old one:

| package                              | role                                                                     |
| ------------------------------------ | ------------------------------------------------------------------------ |
| `@modelcontextprotocol/server` 2.0.0 | McpServer, transports, `inputRequired`, OAuth resource-server middleware |
| `@modelcontextprotocol/client` 2.0.0 | Client, StreamableHTTP/SSE transports, OAuth client machinery            |
| `@modelcontextprotocol/core` 2.0.0   | shared zod schemas                                                       |

The spike proved, over a real v2 client/server round trip:

1. **`registerTool` survives almost unchanged.** New preference: `inputSchema`
   as a single `z.object(...)` (the raw-shape record form still works but is
   deprecated). Annotations ride through as before.
2. **Blocking `server.server.elicitInput()` still works mid-handler** on a
   stateful transport. The stdio path keeps today's confirmation UX with no
   redesign. Clients register the handler as
   `client.setRequestHandler('elicitation/create', …)` (method string, not a
   zod schema — this breaks our test harness's v1 idiom).
3. **The write-once path works and the v2 client auto-drives it.** A handler
   returning `inputRequired({ inputRequests: { confirm: inputRequired.elicit(...) } })`
   is transparently retried by the client after it answers the elicitation;
   the caller of `callTool` just sees the final result. Handler re-runs and
   reads `acceptedContent(ctx.mcpReq.inputResponses, 'confirm')`.
4. **Tool callbacks get `(args, ctx)`** where ctx carries `mcpReq` — replaces
   v1's `extra`. Abort signal location needs confirming during migration.
5. HTTP + OAuth are first-class in the server package: `McpHttpHandler`,
   `PerRequestHTTPServerTransport`, `createMcpHandler`, `OAuthTokenVerifier`,
   `requireBearerAuth`, protected-resource metadata. #303's transport layer is
   mostly assembly, not invention.

## The elicitation decision (resolves the fail-open note in elicit.ts)

Two modes, chosen by transport:

- **stdio (stateful):** keep `confirmDestructive` exactly as designed —
  blocking `elicitInput`, capability-gated, fail-open on absent capability.
  Verified working on v2.
- **HTTP (stateless):** blocking is impossible and fail-open is wrong (the
  transport where parameter guards stop being credible). Guards return
  `inputRequired(...)`; a client that cannot elicit gets a refusal, not a
  silent approval. `confirmDestructive` grows a mode, call sites stay
  unchanged — the thin-wrapper promise holds.

## Phase 1 status: COMPLETE (2026-07-31)

Migrated in one pass, verified four ways:

- **603/603 unit tests green on the split packages**, including the byte-budget
  guard and the cancellation regression test. v1 `@modelcontextprotocol/sdk`
  fully removed (dependency + override) in the same change — no half-migrated
  state ever existed on the branch.
- **tools/list payload SHRANK**: ~6,483 tokens on v2 vs ~6,868 on v1 for the
  same 44 tools — v2's JSON Schema conversion is leaner, and the README's
  ~6,600 claim is honest again.
- **Live stdio smoke against the estate (4.1.2)**: reads work, the
  stop_all_apps guard fired with the real 26-app blast radius, decline aborted.
- **Cross-era compat proven live**: a genuine v1-SDK client (which is what
  Claude Code is today) listed all 44 tools and drove the elicitation guard
  through the version-negotiation boundary. The v2 server negotiates down
  cleanly.

Port surface, for the record: six import sites, `extra.signal` →
`ctx.mcpReq.signal` (14 places), `defineTool` wraps raw shapes in
`z.object()` centrally (the one place all 44 registrations pass through, so
call sites kept their ergonomics), test harness moved to the v2 client
(`setRequestHandler('elicitation/create', …)` — method strings, and v2
`callTool` dropped v1's middle resultSchema argument).

One era subtlety learned: `ctx.mcpReq.elicitInput` is deprecated and
**throws on a 2026-07-28-era request** — blocking elicitation is legacy-path
machinery. `server.server.elicitInput` works today against both eras we can
reach, but Phase 2's write-once guards are the forward path, not an
alternative.

## Migration order

1. **Phase 1 — STDIO parity: DONE, see above.**
   swap imports to the split packages; wrap the 44 raw-shape schemas in
   `z.object()`; port `elicit.ts` internals; port the test harness
   (`Client` from `@modelcontextprotocol/client`, method-string handlers);
   all 603 tests green; live smoke against the estate over stdio.
2. **Phase 2 — HTTP transport (#303):** `McpHttpHandler` +
   `PerRequestHTTPServerTransport`, env-var Coolify token, OAuth resource
   server via `OAuthTokenVerifier`, container image + Coolify deploy for
   estate testing. Write-once guards land here.
3. **Phase 3 — spec extensions where they pay:** structured output (#262,
   `outputSchema` exists on `registerTool` — adopt selectively against the
   token budget), tasks for long deploys (#263), MCP Apps (#264).

## Known hazards, from this session's scars

- The v1 `@modelcontextprotocol/sdk` stays installed until Phase 1 completes,
  then gets removed in one commit — half-migrated imports compile fine and
  fail at runtime.
- The tools/list token budget must be re-measured after migration; v2's JSON
  Schema conversion may emit different shapes than v1's.
- `supportsElicitation`'s doc comment carries the stateless-HTTP warning —
  Phase 2 must resolve it deliberately, not inherit it.
- Anything the type system claims about Coolify responses is unverified until
  probed live. The list is long: `server_uuid`, `project_uuid`,
  `private_key_uuid` on servers — all type-present, wire-absent on 4.1.2.
